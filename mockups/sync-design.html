Versions & conflict — design

.md at the boundary · a store as truth while editing · versions are sources you pull parts from, never auto-merged

Why — the experience this buys

Today, opening the same post on the phone and the mac silently destroys work: whichever device saves last wins. Everything below exists to replace that with five promises:

  • Type anywhere, lose nothing. Any device, any window, offline on a plane — every word survives, always.
  • Look anywhere, see the latest. A session you're only reading follows along as other devices save — the phone as a live preview.
  • The llm contributes without touching your words. Its drafts arrive as versions you pull from, never merged in behind your back.
  • When versions differ, decide per change. See only what diverges; adopt or reject each change atomically — never all-or-nothing, never automatic.
  • Publishing stays boring. The blog still gets a plain .md from git, same pipeline as today.

The posture behind all five: a conflict is not an error to prevent — it is a second version of the post, kept and offered as a source. Everything else in this document is mechanism serving these promises.

A version is the same concept wherever it's born — externally as a file (the llm's draft) or internally when a session diverges (your air while the mini saved). Files are how versions cross the boundary; inside, they're writer-labeled sources. .llm.md already works this way today.

The unit is the post, not the file. Inside the store, a post segments at several depths — the levels where diffs, atomic decisions, and someday deep links operate:

post  ▸  sections (by heading)  ▸  blocks (paragraph · codefence · list item)  ▸  sentences

Which depth reconcile uses is not locked yet — the design only requires that segments are computed from content when needed, never stored.

Writers self-identify — an editable chip with a short device-derived default (mac air ph pad avp), remembered per browser. A session claims its name only when it starts typing — viewing is anonymous (§8).

Commute

patches as algebra — Darcs, Pijul

fork on conflict, human merges — Dropbox copies, CouchDB siblings, Bayou, git branches

cfcms = Embrace, borrowing Merge's one lesson: remember the base. The store knows what every session loaded, so "only the divergent parts" is a 3-way diff, not a guess. Embrace's known failure is orphaned conflict copies that rot unread — because Dropbox and CouchDB had no merge UI. A CMS does: the reference pane already pulls chunks from a version. The historically missing piece is the part that's already built.

3One scenario — the mac and the phone edit the same post

The base is whichever revision of the post a session loaded before typing — what its edits are based on. Every save carries it: "here is my full text, based on v14". The store compares that base against the post's current revision:

base moved and texts differ (the phone above)→kept as the ph version · reconcile offered, never forced

Never happens: overwrite (today's lost-update bug), blocked save (locks), silent machine merge. Offline is the same path — reconnect, save against an old base, your text becomes your version. Offline support costs nothing extra.

4Reconcile — one atomic decision per change

UX contract, no UI decided yet. A divergence is presented as individual changes at segment level; each is its own decision. No "accept all", no automatic merge, and skipping one change never blocks another.

the version…your atomic decision
added a segmentaccept just it — it lands where its neighbours are · or skip it
modified a segmenttake theirs · keep yours — a whole-segment swap
removed a segmentconfirm the removal · keep yours
moved a segmentnothing to decide — position follows content; a move alone is not a difference

Unchanged segments never appear. The base is what makes the verbs possible: knowing what both sides started from is the only way to tell "they added" from "you removed". The llm reference pane already does accept-per-chunk today — this generalizes it to any version, with base-aware verbs.

Decided: a draft must be visible, but not as a file. x.md is written at the publish boundary; the store keeps draft revisions and history. The current per-save file write stays as interim behavior until the store lands — harmless, just no longer the design.

8Writer names — labels with a lease, not identities

A name's only jobs: label a version in the source pane, and scope where a fork lands. Sessions self-identify via an editable chip with a short device-derived default. Typing claims the name; viewing is anonymous — open as many windows as you like, the lease is taken by the first keystroke.

situationresolution
second live session starts typing under a taken nameone server lease per name — newcomer becomes air2; a reconnect within grace is the same session and resumes
named itself offline, arrives to find the name leasedsame rule — suffixed; its pending fork lands under the new label, nothing lost
arrives to find a parked version under its nameidentity by content: identical → same writer for every purpose that exists, resume · different → both versions survive, one suffixed — misattribution impossible either way
llm · extreserved — labels of import paths, never leasable by a session

Same principle as blocks: identity is observational — computed from content when it matters, never stored. No durable tokens that can silently reset; the only state is the lease, which any live connection has anyway. Brainstorm alternative not taken: a persisted random id per browser would answer "same writer?" definitively, at the cost of stored identity that rots when a profile is cleared.
